# Perf audit 01: UI layer

Scope: `lib/viewer/**`, `lib/app.dart`, `lib/main.dart`, `lib/settings/*_screen.dart`, plus the store/photos calls they trigger. Read-only review. Nothing was built, run or measured.

Assumes **n = 40,000 photos**, about 15k with faces and about 30k faces, on a 3-column grid with about 30–45 tiles built (viewport plus cache extent). Frame budget is 8.3 ms at 120 Hz.

Costs are **estimates**. They are scaled from the repo's own figures where one exists: `asset_record_store.dart:2675` says 20k rows ≈ 0.33 s of UI-isolate decode, and `library_index.dart:8` says copying 20k records to an isolate takes 14–60 ms. Confirm the P0/P1 items with a profile build (`_reportJank` in `main.dart`) before you fix them.

Severity:
- **P0**: visible freeze or jank on a common path.
- **P1**: measurable cost (dropped frames, or MB of memory).
- **P2**: minor.

## P0

### UI-1: Cold start: nothing on screen until a full 40k-row read and layout finish
- **Where:** `library_screen.dart:811` (`await reload()`) → `:1289` → `asset_record_store.dart:2695` (full `db.query`, `_fromRow` ×n, `order.sort`). Then `:1297` `LibraryIndex.of`, and `asset_grid_view.dart:347` `PhotoGridLayout.of`, whose day-key memo is empty on first run, so `toLocal()` runs per record.
- **What happens:**
  - sqflite decodes 40k maps × ~30 columns in one synchronous StandardMessageCodec chunk on the UI isolate: ~0.65 s.
  - The 40k sort adds ~20 ms, first layout ~30–60 ms, and the index ~3 ms.
  - `GridSkeleton` is up, but no frame can be produced during the decode.
  - **Scaling:** O(n) in rows × columns, before the first photo appears. Photos opens instantly.
- **Fix:** paint from a small newest-first read, then fill in the rest in chunks.
  ```dart
  // store: first paint
  final head = await db.query(_table, columns: _gridColumns,
      orderBy: 'created_at DESC, local_id DESC', limit: 600);
  // then the rest in chunks, yielding between them
  for (var before = oldest(head); ; ) {
    final rows = await db.query(_table, where: 'created_at < ?', whereArgs: [before],
        orderBy: 'created_at DESC', limit: 5000);
    if (rows.isEmpty) break;
    merge(rows);
    await Future<void>.delayed(Duration.zero);
  }
  ```
  - Narrow the first read to the columns the grid draws.
  - Alternative: a binary grid snapshot file, decoded in `Isolate.run` and returned via `TransferableTypedData`.
- **Risk:** medium.
  - `listAll`'s identity/generation contract (`libraryDelta`) has to cover partial lists.
  - The grid already pins against growth above the viewport (`asset_grid_view.dart:343-372`), so the older chunks landing should not move the view.

### UI-2: Strangers-row face pass runs on the UI isolate
- **Where:**
  - `library_screen.dart:1371-1405` → `findUnnamedFaces` (`unnamed_faces.dart:46-103`).
  - Inside it: `facesByAsset` (`ai_analysis_store.dart:811`), `suggestionsByAsset` (`:217`) and `allDescribedFaces` (`:419`). All three decode on the UI isolate.
  - Then the 15k-candidate `where` + `sort` (`unnamed_faces.dart:54-63`), a string key per face (`:84-87`), and the `Isolate.run` message copy (`:101-103`). That copy is serialized on the sending isolate, i.e. the UI isolate.
- **Triggers:**
  - `firstLoad`: right after the first paint, while the user starts scrolling.
  - `delta.visibility`: every delete, hide or restore.
  - `peopleChanged`.
  - `faces: true`: after naming a face (`:1448`) and after an analyze run (`:1059`).
  - `people_screen.dart:110-146`: on open, and after every name, accept or undo (`:202`, `:216`, `:229`, `:252`, `:260`).
- **Cost:** ~0.2–0.4 s on the UI isolate per trigger. O(faces), not bounded by `scanLimit`, which only bounds the fold.
  - Face JSON for 15k rows: ~50–100 ms.
  - 30k descriptor rows × 512 B (≈15 MB) through the channel: ~100–200 ms.
  - The isolate copy: ~30–60 ms.
- **Fix:** compute where the work already is, and read a small result.
  - Have `AnalyzeQueue` (background work already) persist the top-N folded strangers after each run.
  - The UI then reads ≤60 rows and filters them against `visibleIdsOf(all)` on read.
  - If it must stay live, run the whole function in a background isolate that opens its own DB (sqflite ≥2.3 supports this), so only the ≤60 results cross back.
- **Risk:** the strangers list could be stale between runs. Filtering on read covers hide and delete; naming should invalidate the stored result.

## P1

### UI-3: Full camera-roll re-list on every resume, and every 5 min while the app is open
- **Where:** `library_screen.dart:591` (`_scanRecentThenAll`, which calls `run(force: true)`) and `:1053` (trickle every 20 s, gated by `LibraryScanner.interval = 5 min`, `library_scanner.dart:15`). The pass itself is `photo_library_service.dart:155-184`.
- **What happens:**
  - 40k / 200 = 200 pages. Each page makes `getAssetPathList` + `getAssetListPaged` channel calls (`:95`) plus `store.getByLibraryIds` (`:250`), which decodes full rows over the channel again.
  - Estimate: ~0.8–1 s of UI-isolate decode per pass, in ~200 slices of 4–5 ms.
  - Any slice that lands in a scroll frame drops it, and this happens right after returning to the app.
  - iOS change notifications (`:614-635`) and `syncRecent` already cover live changes.
- **Fix:**
  ```dart
  // resume: recent lane only; full pass only when the library says it moved
  if (await _photoLibraryService.changedSince(_lastToken)) await _libraryScanner.run(force: true);
  ```
  - Back it with PHPhotoLibrary persistent change tokens (iOS 16+), or `assetCount` + newest `modificationDate`. Keep a daily full pass as the backstop.
  - In `_applyPage`, look rows up in the store's in-memory `_records` instead of `getByLibraryIds`.
- **Risk:** a deletion missed while nothing was listening. The change token covers it, and the daily pass is the backstop.

### UI-4: First-scan reload once a second redoes O(n log n) work
- **Where:**
  - `library_screen.dart:985-996` reloads once per second.
  - Each reload with >256 moved rows re-sorts every record (`asset_record_store.dart:2788`).
  - Then `LibraryIndex.of` (`:1297`) and a new `visibleIdsOf` set (`:1379`; memoized on list identity, so it is rebuilt every time).
  - Then a per-person `where` (`:1380-1386`), the album loop over `active` (`:1352-1356`), two membership reads (`:1345`, `:1377`) and `PhotoGridLayout.of` (`asset_grid_view.dart:347`).
- **Cost:** ~40–60 ms every second for the whole first scan, which takes minutes at 40k. That is a hitch of 5–7 frames each time.
  - sort ~20 ms, visible set ~5–8 ms, layout ~5 ms, memberships decode ~10 ms.
- **Fix:**
  - Pages arrive sorted (newest first), so merge them in O(n + k) instead of re-sorting.
  - New photos have no memberships, so skip people and albums when the delta is additions only (add `delta.added` alongside `shape`/`visibility`).
  - Throttle to 2–3 s once the viewport is full.
- **Risk:** low.

### UI-5: Every non-status reload recomputes everything, even when nothing it depends on changed
- **Where:**
  - `library_screen.dart:1340-1356` always runs: album list, `allMemberships`, the loop over 40k `active`, `_loadBuiltInCovers` and `personStore.listAll`.
  - `:1373-1388` runs on any `libraryChanged`: `visibleIdsOf(all)` rebuilds a 40k set, plus a person-membership pass.
- **Triggers:** every `_push` pop (`:2420`), every detail-screen close (`:2108`), and every heart, tag, place or lock edit (`:1873`, `:2042`, `:2069`, `:2346`, `:2364`). The detail screen's heart goes through `_toggleFavorite`, so this cost lands mid-animation.
- **Cost:** ~25–40 ms per heart tap (3–5 frames). About 10–20 ms per pop with no change at all (memberships decode + the 40k loop).
- **Fix:**
  ```dart
  final membersMoved = await _albumStore.revision() != _albumRev || await _personStore.revision() != _personRev;
  if (delta.shape || membersMoved) albumAssets = ...;            // else keep _albumAssets
  if (delta.visibility || peopleChanged || membersMoved) counts = ...;
  // visibleIdsOf: memoise on the store's visibility generation, not on list identity
  ```
  - If `identical(all, _all)` and no revision moved, skip straight to `setState` (or skip it entirely).
- **Risk:** counts go stale if a membership write doesn't bump the revision. Every write path needs a revision counter.

### UI-6: Search runs on the UI isolate per keystroke, with no debounce
- **Where:** `library_screen.dart:2810` (`onChanged: setState`) → `_filtered` (`:1454-1478`).
  - The first non-empty query runs `searchTextOf` for all 40k records (`library_index.dart:74`: list spread + join + `toLowerCase`).
  - Each keystroke then runs 40k `contains`, builds a new list, and runs `PhotoGridLayout.of(m)` plus a re-anchor.
- **Cost:** first keystroke ~40–80 ms freeze; each later keystroke ~5–10 ms, plus layout.
- **Fix:**
  - Debounce at 120 ms.
  - Build the lowercased index in `Isolate.run` when search opens (copying the strings back costs ~5–10 ms, unlike copying records).
  - When the new query starts with the previous one, filter the previous result instead of the whole library.
- **Risk:** low.

### UI-7: Blurred shadow on the cloud badge of every backed-up tile
- **Where:** `asset_grid.dart:611-617`: `Icon(cloud_fill, shadows: [Shadow(blurRadius: 3)])` on every fully backed-up tile.
- **What happens:**
  - On iOS, Flutter 3.47 always uses Impeller, which has no raster cache. The per-row `RepaintBoundary` (the delegate default) reuses the recorded picture but still re-renders it every frame.
  - That is one Gaussian blur per visible tile: 30–45 per scrolling frame on a backed-up library. Estimated 1–3 ms of raster per frame; confirm in DevTools.
- **Fix:**
  ```dart
  Stack(children: const [
    Positioned(left: .5, top: .5, child: Icon(CupertinoIcons.cloud_fill, size: 13, color: Color(0x99000000))),
    Icon(CupertinoIcons.cloud_fill, size: 13, color: CupertinoColors.white),
  ])
  ```
  An unblurred offset copy gives the same legibility with no filter.
- **Risk:** a small visual change.

### UI-9: Album covers and avatars of file-backed photos decode the full original
- **Where:**
  - `_AlbumCard` calls `assetImage(cover, …)` with no `thumbnailSize` (`library_screen.dart:3348`); so does `PersonAvatar` `whole()` (`person_avatar.dart:101`).
  - That reaches `asset_grid.dart:219-228` `Image.file(path, cacheWidth: null)`.
  - `_FaceCrop` decodes up to 3072 px wide (`person_avatar.dart:151-155`) from `FileImage` (`asset_grid.dart:321`).
- **Who it hits:** records with a `sourcePath`: manual adds, edit/resize copies, restored originals.
- **Cost:**
  - A 12 MP cover decodes to 4032×3024 = **48 MB**. A face crop for a 92 pt circle is up to 3072×2304 ≈ **28 MB**.
  - The default `ImageCache` is 100 MB, so 2–3 covers evict every grid tile image. Tiles then re-decode on scroll-back, and memory-pressure kills follow.
- **Fix:**
  - Pass `thumbnailSize: (140 * dpr).round()` for cards and `(size * dpr).round()` for avatars.
  - For face crops, prefer the PhotoKit fitted 1200 px bytes or the 320 px cached thumbnail, and cap `decodeWidthForFace` at ~1536.
  - Use `cacheHeight` for portrait images.
- **Risk:** tiny faces in group shots get a little softer.

### UI-10: One DB query per avatar mount (N+1)
- **Where:** `person_avatar.dart:79`: every `PersonAvatar` `initState` calls `getVisibleByLocalIds`, which runs one SQL query plus a `File.exists` per file-backed row (`asset_record_store.dart:2243-2263`, `:2010`).
- **Where it multiplies:**
  - The People row in the library: up to 20 named + 20 strangers. It is a lazy `ListView`, so avatars are re-queried every time they scroll back in.
  - `PeopleScreen` rows: N people + 60 strangers, so 100+ round trips on open, each decoded on the UI isolate.
- **Fix:** resolve from memory and hand the record in. If a lookup is still needed, read the store's in-memory `_records`.
  ```dart
  final byId = recordsById(all); // memoised per listAll instance, like visibleIdsOf
  PersonAvatar(record: byId[person.avatarLocalId ?? first], ...)
  ```
- **Risk:** low.

### UI-11: Flagged Items re-derives all flags up to 10×/s during a run
- **Where:**
  - `flagged_items_screen.dart:122-213`: `_deriveSoon`, throttled to 100 ms, then `_compute` over all flags.
  - `fix_queue.dart:477-480`: `isResolved` builds `'${flag.id}#${s.name}'` per flag per solution.
  - The queue notifies per step (`fix_queue.dart:448`).
- **Cost:** a fully backed-up 40k library flags about 40k photos as Optimize candidates. That is ~80k string allocations + map lookups + group/fold ≈ 10–20 ms per derive. At 10 Hz that is 10–20% of the UI isolate, and each derive frame overruns the 8.3 ms budget.
- **Fix:**
  - Key `_resolved` by a record `(id, solution)`, or by a key precomputed on `Flag`.
  - Have the queue report the ids that changed, and adjust the counts incrementally.
  - Throttle to 300–500 ms while a run is going.
- **Risk:** low.

## P2

### UI-8: Rounded-rect clip on every tile
- **Where:** `asset_grid.dart:474`, `ClipRRect(BorderRadius.circular(8))`. The default `antiAlias` behaviour means no saveLayer.
- **What happens:** with no raster cache under Impeller, 30–45 rounded clips run every scrolling frame. Photos draws square tiles.
- **Fix:** no clip. Draw the image unclipped, then paint the four corner wedges in the page colour (`0xFF1C1C1E`) on top with one `CustomPaint`. Profile before and after.
- **Risk:** the corner colour must match the background on every screen that hosts the grid.

### UI-12: One fix-queue item or one selection tap rebuilds the whole library screen
- **Where:** `library_screen.dart:767-774` (one `setState` per fix-queue item, even while the screen is under the Flagged route), `:2130` (drag-select), `:2155` (tap-select), and the `_busy` toggles.
- **What happens:**
  - Each rebuild creates a new `SliverChildBuilderDelegate` (`asset_grid.dart:98`), whose `shouldRebuild` is always true, so all built tiles rebuild.
  - Every trailing `SliverToBoxAdapter` subtree rebuilds too, because those are not lazy.
  - Estimated ~2–4 ms per rebuild.
- **Fix:**
  - Put the Flagged count in a `ValueNotifier<int?>` with a `ValueListenableBuilder` around that one row.
  - Put the selection in a `ValueNotifier<Set<String>>`, and wrap only each tile's checkmark overlay in a builder.
  - Cache the delegate in `AssetGridViewState`, keyed on `_layout`.
- **Risk:** medium (callback identity).

### UI-13: Allocations in the per-tile hot path
- **Where:**
  - `asset_grid.dart:161` calls `actionsFor(record)` for every tile build: 5 `TileAction`s, closures and l10n lookups. The library never uses them because it passes `onLongPress` (`:445`).
  - `asset_grid.dart:41` constructs `DateFormat.yMMMd()` on every header build.
  - Other grid screens wrap every tile in a `CupertinoContextMenu` (`:446`): one State + GlobalKey per tile.
- **Fix:**
  - Make `actions` lazy (`List<TileAction> Function()`).
  - Cache the format: `static final _fmt = <String, DateFormat>{}`, keyed by locale.
- **Risk:** low.

### UI-14: Drag-select builds a 40k index on its first move
- **Where:** `select_sweep.dart:38-40` builds a map over `order()`, and `library_screen.dart:2128` builds a list of 40k ids.
- **Cost:** a ~5–10 ms hitch on the first move of every sweep.
- **Fix:** put the record's index into the tile's `MetaData`, as `(record, index)`, and drop the map. Alternatively, memoize the map per `_filtered` identity.
- **Risk:** low.

### UI-15: Timers created and cancelled per scroll frame
- **Where:** `date_scrubber.dart:154-165` (2 Timers per scroll notification) and `scroll_stop_guard.dart:31-33` (1 more).
- **Cost:** ~360 Timer create/cancel pairs per second at 120 Hz. Small, but it is churn on the scroll path.
- **Fix:** store `_lastScrollAt`, keep one timer, and on fire re-arm it only if `now - _lastScrollAt < delay`.
- **Risk:** none.

### UI-16: Platform calls awaited one after another before `runApp`
- **Where:** `main.dart:17-24`: `_ensureTemp`, then `AppStoreRegion.load` (3 sequential calls, `app_store_region.dart:28-32`), then `DemoMode.init` (`getDatabasesPath`, path_provider, `exists`).
- **Cost:** ~6–8 serial round trips before the first frame, ~5–20 ms on a cold start.
- **Fix:** `await Future.wait([_ensureTemp(), AppStoreRegion.load(), DemoMode.init(seedLater: true)])`, and make the region lookup one channel call that returns all three values.
- **Risk:** low. Demo mode must still be settled before `LibraryScreen` mounts, which awaiting the `Future.wait` preserves.

### UI-17: Screen opens re-filter or re-read data that is already computed or cached
- **Where:**
  - `favorites_screen.dart:39-40`, `album_screen.dart:118-122` and `recently_deleted_screen.dart:60-65` filter all 40k records and then re-sort a list `listAll` already returns in `created_at` order. ~3–5 ms per open.
  - `person_page_screen.dart:66-73` re-reads the person's rows from SQLite: full row decode + `File.exists` per file-backed row. ~50 ms for a 3k-photo person.
- **Fix:**
  - Drop the redundant sorts.
  - Hand `FavoritesScreen` the `_favorites` list the library index already computed.
  - On the person page, filter `listAll()` by the person's id set.
- **Risk:** none.

### UI-18: Trickle work every 20 s, and reloads for thumbnails that keep failing
- **Where:**
  - `library_screen.dart:1043`: `_pendingAndFailed` (`sync_engine.dart:93`) is a full `where` over 40k every 20 s, ~3 ms.
  - `:1082-1109` (`_cacheMissingThumbnails`): `_cacheThumbnail` swallows errors (`:1106`) without adding the id to `_unresolvable`, so the same 8 records are owed every round. It then reloads every 20 s indefinitely, at UI-5 cost.
- **Fix:** add failures to a per-session skip set, and only `reload()` when at least one thumbnail was actually cached.
- **Risk:** low.

### UI-19: Hidden album fully reloads for each upload that lands
- **Where:** `private_album_screen.dart:489-491`: each `changed` tick from the backup triggers `_reload`.
  - That runs a `forPasscodeHash` query and a sort, then `_keysOf`, which computes a keyed-hash name per record (`object_key.dart:150`).
  - Then `_sumBytes` stats every file (`:603-614`).
- **Cost:** bounded by album size (hundreds of photos): ~10–30 ms per landed upload.
- **Fix:** patch the one record that changed, recompute its keys only, and sum file sizes once.
- **Risk:** low.

## Checked and fine (no finding)
- **Grid geometry:** `PhotoGridSliver` overrides every O(n) path of `RenderSliverFixedExtentBoxAdaptor` (min/max index, offset, max extent, estimate), so scroll layout is O(log sections). Layout is memoized on list identity and width (`asset_grid_view.dart:333`), with day keys memoized per record (`photo_grid_layout.dart:162-180`).
- **Reload plumbing:** `listAll` is incremental and returns the same instance when nothing moved. `reload()` is single-flight with one queued run (`library_screen.dart:1259-1283`). The drain reloads once per drain, not per job (`:778`). The status-only path skips everything except the tiles (`:1314-1320`).
- **Images:**
  - Thumbnails: requests are cancelled when their tile is disposed (`asset_grid.dart:1073-1076`, `PMCancelToken`). The bytes cache is capped at 2000 entries and the fitted cache at 12. Memory pressure clears both and the `ImageCache` (`library_screen.dart:553-556`).
  - Grid file images use `cacheWidth: 200`.
  - The viewer decodes at screen width, and at ×3 only while zoomed (`detail_screen.dart:1750-1771`).
  - Re-encode runs through `compute` (`detail_screen.dart:452`). Face crops are native, with an isolate fallback (`face_crops.dart:66-75`).
- **Sync file I/O on the UI isolate:** none in scope. `main.dart:94-95` is debug-only, behind `kDebugMode`.
- **saveLayer in the grid:** none. No Opacity, BackdropFilter or ShaderMask. Cloud-only dimming is a flat overlay (`asset_grid.dart:498`). Only uploading underlines animate, each behind its own `RepaintBoundary`.
- **Detail pull gesture:** it rebuilds only the transform and chrome through `ValueNotifier`s (`detail_screen.dart:226`, `:962`). `_ChromeFade`'s `Opacity` covers only the toolbars.
- **Listeners and timers:** removed or cancelled in `dispose` for `LibraryScreen` (`:657-670`), `DateScrubber`, `ScrollStopGuard`, Flagged Items (`:98-106`), Private Album (`_unwatchBackup`), the People undo toast, and video controllers.
- **Settings screens:** small fixed reads only (secure storage, iCloud status). Nothing proportional to library size.
