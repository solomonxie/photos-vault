# Photo Backup App

## Problem
Photo apps like Google Photos/iCloud lock the user's photos into a vendor's storage and pricing. Need an iPhone app that backs up the camera roll to a bucket the user owns and controls, while still browsing/viewing as fast as a native gallery. Android is on the roadmap but backlogged — see Non-goals.

## Goals
- Auto-backup new/changed Photos/Videos to the user's own S3 bucket, incrementally. iOS first.
- Manual backup too, not just auto-detected camera-roll assets: pick files from the Files app, pick specific photos/videos, or receive a file shared from another app via the Share Sheet — all enqueued into the same pipeline.
- Support multiple configured backup targets (AWS S3, Tencent COS and Alibaba Cloud OSS now; other object-storage vendors planned), each validated for real bucket access before being saved (provider + bucket + credentials + prefix). With multiple targets, the user picks the traversal order: mirror each photo to every target before the next photo, or fill one target completely before starting the next.
- Generate thumbnail + medium + original derivatives on-device before upload. Every photo also keeps its thumbnail locally, including ones already small enough to skip the separate `thumbnails/` upload — that cached copy is what the grid draws once the full-resolution local original has been deleted.
- Reclaim device storage per photo: "Remove from Device" drops the full-resolution local copy (from the OS photo library itself, for a camera-roll asset) while keeping the backed-up one. The photo stays in every library view as its thumbnail, and its detail screen offers to pull the original back down from the bucket.
- Upload each derivative under a distinct, clearly separate S3 key prefix (`thumbnails/`, `medium/`, `originals/`) so the user's own bucket Lifecycle Rules can target each class independently — storage class/tiering is entirely the bucket owner's concern, set up outside the app; the app's only job is the clean prefix split.
- In-app viewer: thumbnail-first grid, progressive load to full res on open.
- Survive backgrounding/app kill/network loss; resumable uploads for large videos.
- i18n from the start: every user-facing string goes through the localization layer, not hardcoded — English and Mandarin (Simplified) supported now, more locales just add an ARB file later.
- Private Albums (Utilities): a 4-digit-passcode-gated hidden space. The passcode *is* the album id — no separate "wrong passcode" state, so a mistyped/forgotten code just opens an empty album instead of an error (plausible deniability, same trick as Signal's hidden-chat PIN). Supports move/copy in from the full library and whole-folder delete; header shows item count + total size.
- People profiles: each recognized person gets more than a name — a full editable profile (bio fields, AI-assisted initial fill from their photos), an optional per-profile passcode+hint lock, links to other people with a typed relationship (family/friend/colleague/...), a net-graph view of those links, and geolocation movement history (origin + relocations, not trip/travel history).

## Non-goals (v1)
- **Android build/test/release — backlog, not abandoned.** The Flutter codebase already runs on Android (scaffold builds for both), but Android-specific verification, permission-flow testing, and Play Store release are deferred until iOS is solid.
- **Consumer cloud-app destinations (iCloud Drive, Google Drive, Dropbox, etc.).** The whole point of this app is storage the user owns and controls; anything backed by another vendor's app-managed cloud already has an official app that does that job perfectly well. (Other *object storage* vendors are a different case: same user-owned-bucket model as S3. Tencent COS and Alibaba Cloud OSS are built; Google Cloud Storage, Azure Blob and Backblaze B2 aren't, and the Add Backup storage-type picker lists those as "coming soon".)
- Multi-device sync / shared library.
- Managing S3 Lifecycle Rules from inside the app (user configures these directly in AWS).
- Web/desktop platforms (mobile only).
- Multi-resolution video transcoding (poster-frame thumbnail + original only, in v1). Until a video *does* get a poster frame (T2.3), videos have no thumbnail to fall back on, so "Remove from Device" isn't offered for them.
- STS/Cognito temporary credentials — static IAM user keys only (single-user personal app, no backend to broker tokens).
- True OS background scheduling (`BGTaskScheduler`) for the configurable sync frequency — that's a separate, real iOS background-execution feature to register for later. Today's `SyncFrequency` is opportunistic: checked when the app comes to the foreground, not while backgrounded/closed. (Unrelated to — and doesn't affect — an *upload already in flight* surviving backgrounding, which `background_downloader`'s native transfer already handles per the Goals above.)

## Options considered
- **Platform**: native Swift+Kotlin (two codebases) vs React Native/Expo vs Flutter/Dart → Flutter wins: one Dart codebase, and `flutter run` produces a real compiled native app from day one — no sandboxed dev runtime standing between the app and native background-transfer APIs. Kept even though Android is now backlogged: it costs nothing to build iOS-only for now on a codebase that's already Android-ready, versus committing to a native Swift rewrite if/when Android gets prioritized.
- **Expo Go: ruled out, and nothing in this repo depends on it.** Flaky in practice, and it wants an account and a login before it will run your own app on your own phone — an extra hop, an extra service and an extra failure mode between a code change and seeing it. For a one-person personal project that buys nothing: the payoff it's built for (sharing a dev build with a team, CI-less distribution) never applies here, while the costs — a sandboxed runtime that can't reach the native background-transfer and Photos APIs this app is *made of*, plus two ways to "run the app" that behave differently — apply every day. `flutter run` and `xcrun devicectl device install app` are the only two paths, with nothing in between to be confused by.
- **AWS access**: full AWS SDK vs on-device SigV4 presigned URLs + a native background-transfer package → presigned URLs win, same reasoning as any mobile client: keeps the bundle light and lets uploads run through a package that wraps native `URLSession`/`WorkManager` transfer instead of the SDK's own HTTP stack.
- **Background transfer package**: hand-rolled platform channels vs `background_downloader` (pub.dev) → `background_downloader` wraps native `URLSessionUploadTask` (iOS) and `WorkManager` (Android) for resumable, backgrounded uploads out of the box — avoids writing and maintaining two sets of platform channel code.
- **SigV4 signing**: hand-rolled HMAC-SHA256 vs the `aws_signature_v4` package (pub.dev, from the AWS SDK for Dart family) → use the package: it's maintained by AWS, removes the "fiddly to get right" risk a hand-rolled signer would carry.
- **Large file transfer**: single PUT vs S3 multipart → multipart above a size threshold: resumability over cellular, each part as its own `background_downloader` upload task.
- **State/metadata store**: local SQLite (`sqflite`) vs S3-hosted manifest → local SQLite: v1 is single-device, no cross-device merge needed; S3 only holds asset bytes (+ optional per-asset JSON sidecar for future multi-device use).
- **Storage tiering**: app sets `x-amz-storage-class` at upload vs leaves it entirely to the bucket owner → entirely to the bucket owner. The app has no opinion on Standard/IA/Glacier — it just keeps derivatives under clearly separate prefixes; storage-class decisions belong to the S3 account owner's own Lifecycle Rules, configured outside the app.
- **Multiple buckets**: single configured bucket vs a list of backup targets → a list. Nothing about backup requires exactly one destination, and letting the config live as a list from the start avoids a later migration.
- **Backup destination scope**: S3-only vs also support consumer cloud-app destinations (iCloud Drive folder, etc.) → excludes consumer cloud apps only. A folder-style target backed by one of those was prototyped (T1.7/T1.8) and dropped: this app's reason to exist is storage the user owns, not another vendor's managed cloud — those already have official apps. Other *object storage* vendors don't have that conflict — same user-owned-bucket model as S3 — so Tencent COS and Alibaba Cloud OSS are now wired up alongside it, and the picker still lists GCS, Azure Blob and B2 as a roadmap item ("coming soon").
- **Multi-target order**: always mirror per-photo vs let the user choose → configurable `BackupOrderStrategy` (`fileByFile` default, or `bucketByBucket`). Either way every photo ends up on every target — this only changes the order uploads happen in, not the outcome, so it was safe to make a simple user preference rather than a bigger redundancy/sharding decision.
- **Reaching COS and OSS**: each vendor's own SDK/protocol vs their S3-compatible endpoints → S3-compatible endpoints. Both document them for AWS SDK users, both accept SigV4 under service `s3`, so one signer, one uploader, one bucket browser and one set of error codes cover all three providers; the entire per-provider difference is a hostname (`lib/settings/bucket_endpoint.dart`). COS's bucket name carries its APPID suffix; OSS answers the S3 API on an `s3.`-prefixed host and ignores the region in the credential scope (its own examples pass anything), so the bucket's real region is used for both host and scope.
- **Region entry**: manual region field vs auto-detect from the bucket name → auto-detect where it exists, pick-or-type otherwise. S3's global endpoint returns the bucket's home region in the `x-amz-bucket-region` response header even on an unauthorized request, so for S3 the user only ever types the bucket name. COS and OSS have no equivalent, so the form offers their published region lists as suggestions over a free-text field — a closed dropdown would lock out any region added after a release — and a pasted endpoint/console URL fills it in without typing.
- **Validating new backup targets**: save first vs validate access, then save → validate first. A signed `HEAD` request against the bucket (needs `s3:ListBucket`, the same permission actual backups will need) runs before the entry is persisted, so a typo'd bucket name or bad key never silently sits in the list.
- **i18n**: retrofit later vs wire it in at the scaffold stage → wire it in now, via Flutter's own `flutter_localizations` + `intl` + ARB files (`flutter gen-l10n`) rather than a third-party package — it's the framework-native approach, and retrofitting after screens exist means re-touching every hardcoded string later.
- **Private Album passcode UX**: show "incorrect passcode" on a miss vs treat every 4-digit code as valid (existing → that album; new → freshly created empty album) → treat every code as valid. Erroring on a miss both leaks "an album exists at all" to anyone who tries a few codes, and (worse) if the *real* passcode gets mistyped once and rejected, the user never gets a hint they picked wrong — going straight to a blank album on any code sidesteps both.
- **Private Album passcode storage**: store the 4 digits themselves as the row key vs hash them → hash (existing device-local pattern: `flutter_secure_storage` already holds S3 keys; passcode hash can live in `sqflite` since it's not itself a secret worth OS-keychain protection, just an app-level lock) — keeps a `sqflite` DB dump from directly listing which 4-digit codes are in use.
- **Private Album membership**: a nullable `privateAlbumId` tag on `asset_record` (copy = a second, distinct row) vs a `private_album_asset` join table, mirroring `album_store.dart` → join table. A distinct row-per-copy sounded simpler at first, but `manualFile` `localId`s are content-hash-derived (`manual:$hash`) — a "copy" of already-tracked content can't get a second distinct row without breaking that dedup invariant, and a synthetic id for a `photoManager`-sourced copy would break its `entityIdFrom` resolution. The join table sidesteps both: "move" tags a `moved: true` membership row and separately hides the (single, shared) `asset_record` via the existing `isHidden`; "copy" tags `moved: false` and touches nothing else — the asset stays exactly where it already was, visible everywhere it already showed up, now also listed here.
- **Person identity**: on-device face-recognition clustering vs manual "this is the same person" tagging seeded from existing AI vision analysis → manual tagging first, on-device clustering as a later stretch goal. `ai_vision_service.dart` today returns a people *count* per photo, not identity — an on-device face-embedding model (e.g. via `google_ml_kit` or similar) is real added scope; shipping manual tagging first (the user confirms "this is Alice" once, subsequent photos of Alice attach to the same `Person`) gets profiles usable without it.
- **Relationship graph rendering**: hand-rolled `CustomPainter` layout vs a pub.dev graph package (`graphview`) → hand-rolled, reversing the original call: the actual layout need — union-find family-type relationships into clusters, place each cluster around a circle, members around their cluster's center — is simple enough that a general force-directed graph package would be more API surface to wire up (and one more dependency) than the ~40 lines of layout math it replaces; `graphview`'s real value (arbitrary force-directed layouts) isn't needed here.
- **AI-assisted profile fill**: authoritative auto-fill vs suggestion-only → suggestion-only, same opt-in/user-supplied-API-key model as T4.4's People/Events analysis. Bio fields (job, education, family) are exactly the kind of thing a vision model will confidently hallucinate; auto-filled fields are pre-filled but always user-editable, never asserted as fact.

## Decision
Flutter app, developed and tested against **iOS first**; Android stays buildable from the same codebase but is backlog for verification/release. Settings holds a **list** of `S3BackupTarget`s in `flutter_secure_storage` (provider, accessKeyId, secretAccessKey, region, bucket, prefix). "Add Backup" picks a provider (S3, COS, OSS), auto-detects the bucket's region from its name for S3 or takes a picked/typed one otherwise, then runs a signed connectivity check (`aws_signature_v4` + `http`) against the entered bucket before saving — failures (forbidden/not-found/network) are shown inline and nothing is persisted until it passes. The key prefix field defaults to `bring-your-own-photos/` so there's nothing to think up.

`photo_manager` enumerates the camera roll; a manual add flow (`file_picker` for Files-app documents, `photo_manager`'s picker for specific photos/videos) and an iOS Share Extension (`receive_sharing_intent`, files shared in from other apps) feed the same queue for anything not auto-detected. A local pipeline (`image` package + `video_thumbnail`) generates {thumbnail, medium, original-passthrough} derivatives. Each derivative is PUT via a presigned URL through `background_downloader` upload tasks (multipart for large files), landing under a prefix-separated key layout (`thumbnails/`, `medium/`, `originals/`) so the user's own S3 bucket Lifecycle Rules can do all storage-class tiering — the app has no storage-class concept at all. Upload/dedup state lives in local `sqflite`. All UI strings are routed through `AppLocalizations` (generated from `lib/l10n/app_{en,zh}.arb`) from the first screen onward — `en` and `zh` (Simplified) ship now.

**Private Albums**: reuses the existing Utilities "Hidden" row (no new row) — tapping it opens a passcode sheet (4-digit entry + "Enter" + "Create New"). Both buttons behave identically except when the hashed code matches an existing `private_album` row: `Enter`/`Create New` on a match opens it; `Enter` on no match shows a fresh, empty (unsaved-until-used) album at that code; `Create New` on no match persists a new `private_album` row for that code, then opens it. The same sheet gates the grid tiles' long-press "Hide" action too, replacing the old plain-toggle version. The private album screen reuses `asset_grid.dart`'s grid, adds a header (item count, total size — best-effort, no forced iCloud fetch), a library picker (shared `AssetPickerScreen`, also used by People's "Add Photos") to move/copy assets in, and a "Delete Album" action that un-hides any moved-in assets and deletes the album + its membership rows — nothing is destroyed, mirroring `AlbumStore.remove`'s own precedent — after a confirm sheet.

**People profiles**: `SmartCollectionScreen`'s People grouping (currently by AI-detected people-*count*, no identity) grows a `Person` entity — name, profile photo, bio fields (education/job/family/relatives), a `PersonProfileScreen` reachable via a chevron next to the name, per-profile passcode+hint lock, typed links to other `Person`s (family/spouse/parent-child/friend/colleague/...), a hand-rolled-`CustomPainter` relationship net graph (family clustered in a circle, other relations styled by line color/type), and a geolocation movement history (origin + relocation entries — manual entry today; sourcing from EXIF GPS clustered over time is still open, pending Places' EXIF extraction). Identity starts as manual "+ Add Person"/"Add Photos" tagging, not seeded from per-photo AI analysis yet; face-clustering automation is a later stretch. AI-assisted bio auto-fill (pre-filled but always user-editable, never authoritative) is likewise still open — bio fields are blank until the user fills them in.

## Risks / open questions
- If a lifecycle rule has already moved an original to Glacier/Deep Archive, viewing it requires a `RestoreObject` call and a multi-hour wait — app must detect `InvalidObjectState` and show "restoring", not fail silently.
- iOS background execution has its own throttling (BGTaskScheduler budget) even with a native transfer package — needs on-device testing, not just the simulator.
- `photo_manager` exposes less low-level resource detail than PhotoKit directly — Live Photos and bursts need explicit verification.
- Static long-lived IAM keys stored on a phone is an accepted risk for a single-user app with no backend — mitigated only by secure-storage + a least-privilege IAM policy scoped to one bucket/prefix.
- **Backlogged, revisit when Android is prioritized**: WorkManager can be killed early by aggressive manufacturer battery-optimization (Xiaomi/Huawei/OnePlus); Android scoped-storage rules (API 29+) may limit media access without extra permission flows. Neither blocks iOS-only work now.
- "Mandarin" was assumed to mean Simplified Chinese (`zh`, matching mainland China's writing system) rather than Traditional (`zh-Hant`, Taiwan/Hong Kong) — flag if Traditional was actually wanted, it's a one-ARB-file swap.
- A 4-digit passcode is 10,000 combinations — fine as a casual "keep it out of a quick phone-borrow" lock, not real encryption-at-rest; private-album derivative files sit unencrypted on disk under their own dir like any other asset. Flag if actual at-rest encryption (not just UI-gating) was expected.
- Deleting a Private Album un-hides any moved-in assets back to the library rather than deleting them — safer than the outright-delete originally sketched here, and consistent with `AlbumStore.remove`'s existing "membership only" precedent. Flag if outright deletion (with a confirm) was actually wanted instead.
- Person-profile lock scope (lock the whole profile vs. just the bio/sensitive fields, photos still visible) is assumed to be "hide bio info only, photos stay visible" per the request's "lock it ... to lock view info" wording — flag if it should hide the person's photo grid too.
